## 1. ゲーム概要

ベルトコンベアで上から下へ流れてくる「はにわ」と「土偶」を、左（はにわ）・右（土偶）に正しく仕分け続けるエンドレス型の2択ゲーム。
PC（キーボード）とスマートフォン（タッチ）の両方で、ブラウザだけで遊べる。ミス3回で終了し、スコアを競う。

## 4. 問題点・矛盾の指摘

### 4.1 判定まわり

**P-01 先行入力エリアと通常判定エリアは、判定結果がまったく同じ。**
どちらも「押した瞬間に正誤判定」で、得点にも差がない。つまり機能上は「判定可能時間1.50秒の1つの窓」と同じになる。
違いが出るのは「画面にどう見せるか」だけなので、先行入力エリアの意味を決める必要がある（→ D-03）。
解釈案：画面に描く判定枠は通常判定エリアだけで、先行入力エリアは「少し早く押しても無視されない、見えない猶予」。これなら初版の意図（早めに押した人を救う）と矛盾しない。

**P-02 判定時間を「秒」で決めると、速度を上げる方式（A・C）と相性が悪い。**
判定エリアは画面上の場所（枠）として描かれる。速度が2倍になると、
- 判定時間（秒）を固定する場合：枠の長さが2倍に伸びる。暫定表の最終段（2.1倍）では、判定枠が画面の約9割を占め、待機エリアがほぼなくなる（付録A）。
- 枠の長さを固定する場合：判定時間が短くなる（2.1倍で1.50秒→約0.71秒）。

方式B（速度一定）ならどちらでも同じなので問題は出ない。速度を上げる段階を作るなら、どちらを基準にするか決める必要がある（→ D-02）。

**P-03 「同時押しは無効」と「押した瞬間に判定」を両立させるには定義が必要。**
先に押した方はその瞬間に判定済みなので、後から「同時だったので両方無効」にはできない。
また、速く交互に押す人は「左を離す前に右を押す」（ロールオーバー）ことが多い。「反対のキーが押されている間は無効」と単純に決めると、正しい速い入力が無視され、見逃しミスにつながる（→ D-06）。
スマホでは両手の親指で2つのボタンを同時に触れる場合が同じ問題になる。

**P-04 不正解だった出土品の行き先が決まっていない。**
「1回の押下につき1個を処理」とあるので、押した時点で出土品が消費される（コンベアから外れる）と読むのが自然。
もしコンベアに残すと、ミスの直後にもう一度押して正解にでき、さらに判定ライン通過で2回目のミスにもなりうる（→ D-05）。

**P-05 待機エリアで押した入力は、何の反応もなく無視される。**
テンポよく押す人は「押したのに仕分けられていない」ことに気づきにくい。罰がないのは良いが、軽い反応（ボタンが小さく揺れる程度）を出すかどうかは演出として決めておきたい（I-04）。

### 4.2 出現パターン

**P-06 「交互出現」「同分類の連続」をそのまま作ると、確実に予測できてしまう。**
C-30「何回連続しても次を確定的に予測できない」と矛盾する。
例：交互パターンが8個続くなら、はにわ・土偶・はにわ…と見た時点で残りが全部わかる。
対策：パターンを「確率の偏り」として作る。たとえば交互パターン中も「前と違う分類になる確率80%」とし、どの1個も必ずどちらにもなりうる（→ D-07）。
同様に「◯回続いたら必ず切り替える」という上限も入れてはいけない（入れると予測できる）。

### 4.3 難易度

**P-07 方式B（出現頻度だけを上げる）は、いつか上げられなくなる。**
速度が一定のまま出現間隔を縮めると、出土品同士の間隔が縮まる。C-15・C-34（重ならない）があるので、間隔は「出土品の大きさ＋すき間」より小さくできない。
試算では、基準速度のままだと出現間隔の下限は約0.6〜0.7秒（毎秒1.5個前後）になる（付録A）。
2択を毎秒1.5個は、慣れた人なら長時間続けられる可能性が高い。すると「難易度が上がらない＝終わらない」状態になり、エンドレス型として成立しない。
→ Bを主体にするなら、下限に達した後に何か別の上げ方が必要（→ D-01）。

**P-08 暫定の難易度表は、実質的に「画面上の間隔を一定に保ったまま全体を速くする」設計になっている。**
「速度倍率 × 出現間隔」を計算すると 2.00／2.04／2.10／1.98／1.89 で、ほぼ一定。
つまりこの表は方式Cで、画面上の出土品の間隔は変わらず、流れる速さと処理量（毎秒0.5個→1.1個）が上がる。
この表を方式Bに読み替えると、同じ処理量でも画面上の間隔が半分以下に詰まり、見た目の印象がかなり変わる。表の数値はそのまま使えないので、方式決定後に作り直す（→ D-17）。

**P-09 序盤がゆっくりすぎる可能性。**
最初の20個は2.0秒間隔なので、序盤だけで約40秒かかる。2択で1個2秒は、慣れた人には退屈になりうる。
暫定表どおりだと400個到達まで約7.5分（付録A）。目標プレイ時間を先に決め、それに合わせて数値を作る方がよい（→ D-17）。

### 4.4 結果画面・進行

**P-10 ゲームオーバー画面の項目が§5と§10で違う。**
§5：最終得点・仕分け数・最大コンボ・正答率・プレイ時間。§10：最終スコア・最大コンボ・正解数・ミス数・正答率・プレイ時間・リトライ。
「仕分け数」と「正解数」のどちらか（両方か）、正答率の分母に見逃しを含めるか、プレイ時間に一時停止を含めるかが未定義（→ D-08）。

**P-11 一時停止を使うと「止めて考える」ことができる。**
一時停止中に出土品が見えていると、止めて次の数個を確認し、再開直後に押すことで判断時間を稼げる（→ D-09）。

**P-12 ゲームオーバー直後の誤操作。**
3回目のミスの瞬間、プレイヤーは連打中であることが多い。リザルトのリトライ操作がすぐ効くと、結果を見る前に誤ってリトライしてしまう（→ D-10）。

### 4.5 出土品の見た目

**P-13 「色・サイズで判別できない」と「考古学的に正しい」はぶつかる部分がある。**
実物は、埴輪は赤褐色の素焼きで大型（1m前後のものも多い）、土偶は小型（10〜30cm程度が多い）で色味も異なる傾向がある。
実物どおりの色と大きさで描くと、形を見なくても色と大きさで判別できてしまう。
対策：形（シルエットと特徴）は考古学的に正しく描き、色と表示サイズは両分類で共通の範囲からランダムに選ぶ（→ D-14）。

**P-14 見た目の種類が少ないと、すぐ覚えられて「反射だけ」のゲームになる。**
種類を増やす、似ていて迷う組み合わせ（座った人物埴輪と合掌土偶など）を入れる、角度や表情に揺らぎを入れる、などで判断の面白さを保てる（I-01）。

### 4.6 スマホ対応で生じる問題

**P-15 Escキーの扱いが不明。**
追加指示のPC操作は「A/←・D/→・Space」の3つで、初版の「Esc：メニュー」が書かれていない。削除したのか、書き漏れなのかが不明（→ D-09）。
また初版のSpaceは「一時停止・再開」、追加指示では「一時停止」。再開もSpaceでよいか確認したい。

**P-16 スマホの横画面では、縦方向の長さが足りない。**
横向きのスマホは画面の高さが約330〜400ピクセルしかない。縦に流れるコンベアをそこに収めると、出土品は約50ピクセル（約8mm）程度まで小さくなり、C-38（判別しやすい大きさ）を満たしにくい（付録A）。
横画面だけコンベアを横向きに流すとC-13（上から下）を変えることになるため、勝手には行わない（→ D-19）。

**P-17 PCとスマホの公平性。**
画面の大きさが違っても、ゲームの中身（判定時間、出土品が見えている時間、間隔）は同じでなければならない。
そのため、ゲームロジックは画面のピクセルではなく「論理座標」（例：コンベアの長さを1000とした座標）で動かし、描画のときだけ画面に合わせて拡大縮小する必要がある（→ D-02）。
タッチ入力は機種によってキーボードより数十ミリ秒遅れることがある。イベントの発生時刻（タイムスタンプ）で判定するなどして、処理の遅れによる差を小さくする。
画面表示そのものの遅れは機種ごとに違い、完全には揃えられない（判定窓が1.5秒あるので影響は小さいと推測）。

**P-18 iPhoneのSafariでは、ページ設定だけではダブルタップ拡大を確実には止められない。**
画面の拡大禁止設定をSafariは無視するため、CSSの `touch-action` 指定、タッチイベントの既定動作の停止、長押しメニューと文字選択の禁止などを組み合わせる必要がある。
クリックイベントは指を離したときに発生し遅れるので、指が触れた瞬間（pointerdown / touchstart）で判定する（→ D-13）。

**P-19 片手操作では、下部の左右ボタンの端まで親指が届きにくい。**
左右ボタンを画面下部いっぱいに広げ、中央の境目付近でも押せるようにすると、片手でも親指の移動が小さくて済む（→ D-12）。

**P-20 タッチとキーボードの両方がある機器（タッチ対応ノートPC、キーボード付きタブレット）。**
どちらの入力も常に受け付け、画面上のボタンを表示するかどうかだけを機器の種類で切り替える必要がある（→ D-12）。

**P-21 iPhoneのSafariでは音を鳴らすのにユーザー操作が必要。**
タイトル画面の「スタート」をタップしたときに音声を有効化する必要がある（音を入れる場合。→ D-15）。

優先度：**A**＝詳細設計の前に必須／**B**＝詳細設計中に決めればよい／**C**＝調整段階で決めればよい。

### 6.1 ゲームルール

**D-01 難易度の上げ方【優先度A】**

| 案 | 内容 | 起きること |
|---|---|---|
| A | 速度だけ上げる | 判定時間が短くなり、反射神経の勝負になる。速度の上限（人の反応時間）で頭打ち |
| B | 出現頻度だけ上げる | 判定時間は一定、画面に並ぶ数が増え、先を読む力の勝負になる。間隔の下限（約0.6〜0.7秒）で頭打ち（P-07） |
| C | 両方上げる（暫定表はこれ） | 見た目の間隔はほぼ一定で、全体が速くなる |
| **B→C（推奨）** | 序盤〜中盤はBで出現頻度を上げ、間隔が下限に達したら、間隔を下限に保ったまま速度を上げる | Bの「先読みの面白さ」を活かしつつ、エンドレスとして必ず終わりが来る |

推奨理由：指示書がBを推奨しているので主体はBとする。ただしBだけでは上限があるため（P-07）、上限後だけ速度を上げる。
代替：B単独で、下限到達後は見た目の難しさ（I-01）で上げる方法もあるが、終わらないプレイヤーが出る可能性が残る。

**D-02 判定エリアの基準（時間か距離か）【優先度A】**
- 推奨：ゲームロジックは論理座標で動かし、判定エリアは**論理座標上の長さ（画面上の枠）で固定**する。基準速度のときに先行0.35秒・通常1.15秒になる長さに設定する。
  - B段階（速度一定）では指示書の秒数がそのまま守られる。
  - 速度を上げる段階（B→Cの後半）でのみ判定時間が短くなる。これが速度上昇による難しさの正体になる。
- 代替：判定時間（秒）を固定し、速度に応じて枠を伸ばす。速度上昇段階で待機エリアが縮み、先が見えなくなる（P-02）。

**D-03 先行入力エリアの見せ方【優先度A】**
- 推奨：画面に描く判定枠は通常判定エリアのみ。先行入力エリアは枠の少し手前の「見えない猶予」とする（開発用のデバッグ表示では見える）。
- 代替：先行入力エリアも薄く描く。画面の情報が増え、プレイヤーは「どこから押せるか」を正確に知れる。

**D-04 コンボ倍率の適用タイミング【優先度A】**

| 案 | 内容 | 例 |
|---|---|---|
| **加算後（推奨）** | 正解でコンボを+1した後のコンボ数で倍率を決める | 10個目の正解で「10 COMBO」と同時に +120 |
| 加算前 | 押す直前のコンボ数で倍率を決める | 10個目の正解は +100、11個目から +120 |

推奨理由：画面に出る「コンボ数」と「その時の得点」が一致し、節目の手応えがすぐ出る。
加算前の場合、倍率表の「0」行が実際の得点計算に使われる点で表とは素直に合う。どちらでも数値の矛盾はない。

**D-05 不正解だった出土品の扱い【優先度A】**
- 推奨：押した側の回収箱へ飛ばし（×印などで間違いを表示）、コンベアから外す。次の出土品が先頭になる。
- 代替1：その場で砕ける・弾かれて消える演出（どちらの箱にも入れない）。
- 代替2：コンベアに残す（P-04の理由で非推奨）。

**D-06 同時押しの定義【優先度A】**

| 案 | 内容 | 問題 |
|---|---|---|
| a | 反対側が押されている間の入力はすべて無効 | 速い交互入力（ロールオーバー）が無視され、見逃しミスが増える |
| b | 1フレーム分ためてから判定し、同じフレームに左右両方あれば両方無効 | 「押した瞬間に判定」より最大1フレーム遅れる |
| **c（推奨）** | 先に押した方を有効にして即判定。その後、反対側の押下が「先の入力がまだ押されている」かつ「40ミリ秒以内」なら無効 | なし（40ミリ秒は設定値で調整可能） |

キーの自動リピート（長押し）は常に無視。タッチも同じ規則を使う。

**D-07 出現パターンの中身【優先度A】**
推奨：パターンはすべて「確率の偏り」として作り、どの1個もはにわ・土偶の両方になりうるようにする（P-06）。

| パターン | 重み（確定） | 推奨する中身（初期値・調整可） |
|---|---|---|
| 完全ランダム | 50 | 各50% |
| 同分類の連続 | 20 | 「前と同じ分類」になる確率75% |
| 交互出現 | 15 | 「前と違う分類」になる確率80% |
| 片方に偏る | 15 | パターン開始時に偏る側を50%で決め、その側75%・反対25% |

- 抽選し直す個数：8個ごと（設定値）。
- どの1個も、どちらかの分類になる確率が20%を下回らないようにする（予測不能の保証）。
- 「◯回連続したら切り替える」という上限は入れない。
- 長い目で見ると、はにわ・土偶はそれぞれ約50%になる（すべてのパターンが左右対称のため）。

**D-08 ゲームオーバー画面の項目と定義【優先度A】**
推奨：§5と§10の和集合にし、用語を定義する。

| 項目 | 定義 |
|---|---|
| 最終スコア | 合計得点 |
| 正解数 | 正しく仕分けた数 |
| 仕分け数 | 押して処理した数（正解＋誤仕分け） |
| ミス数 | 3（内訳：誤仕分け◯・見逃し◯） |
| 最大コンボ | プレイ中の最大コンボ数 |
| 正答率 | 正解数 ÷（正解＋誤仕分け＋見逃し）。小数1桁の％ |
| プレイ時間 | 開始からゲームオーバーまで。**一時停止中は含めない** |
| ベストスコア | D-16で保存する場合のみ。更新時は強調表示 |

### 6.2 進行・操作・画面

**D-09 一時停止とメニュー【優先度A】**
推奨：
- 一時停止画面＝メニュー（再開・リトライ・タイトルへ・操作説明）とする。
- PC：Spaceで一時停止／再開。Escも一時停止メニューを開く（初版の「Esc：メニュー」を残す）。スマホ：上部の一時停止ボタン。
- 一時停止中はコンベア上の出土品を隠す（P-11対策）。再開は即時（カウントダウンなし。カウントダウン中に出土品が見えると同じ問題になるため）。
- 画面が非表示になった、ウィンドウが選択から外れた、画面の向きが変わった、のいずれかで自動的に一時停止する。

確認したいこと：Escを残してよいか（P-15）。

**D-10 ゲームオーバー時の流れ【優先度A】**
推奨：3回目のミスの瞬間にコンベアと入力を止める → 約1秒の終了演出 → リザルト表示。
リザルトは表示後0.8秒間リトライ操作を受け付けない（P-12）。リトライはボタン（クリック・タップ）とEnterキー／Rキー。
Spaceはボタンに焦点がある状態で押されると誤ってリトライになるため、リザルトではSpaceを無効にする。

**D-12 画面レイアウト【優先度A】**
推奨：

| 画面 | 配置 |
|---|---|
| スマホ縦（基本） | 上：スコア・コンボ・ミス・一時停止ボタン／中央：縦コンベア／下：左右に大きな「はにわ」「土偶」ボタン。下部の幅いっぱいを左右2分割し、中央の境目近くでも押せる（片手対応）。**ボタン自体を回収箱として扱い**、仕分けた出土品がボタンへ飛び込む |
| スマホ横 | 中央に縦コンベア、左右の端に縦長のボタン（両手の親指の位置）。出土品が小さくなるため「縦画面推奨」の表示を出す（D-19） |
| PC | 中央に縦コンベア、左右に回収箱、箱の近くにキー表示（A/←、D/→）。画面上のボタンは非表示（マウスで押せるようにするかは任意） |

- 画面上の仕分けボタンは、タッチ操作が可能な機器（`pointer: coarse` の判定、または最初のタッチ）で表示する。キーボードは常に受け付ける（P-20）。
- iPhoneの切り欠き部分（セーフエリア）を避けて配置する。
- 出土品の表示サイズ目標：スマホ縦で約80ピクセル（約13mm）以上（付録Aの試算。詳細設計で確定）。

**D-13 タッチ入力の方式【優先度A】**
推奨：
- 指が触れた瞬間（pointerdown）に判定。クリックイベントは使わない。
- 押し続けても1回だけ。指をボタンの上で滑らせて反対側のボタンに入っても入力しない。
- ゲーム画面では `touch-action: none`、文字選択・長押しメニュー・ダブルタップ拡大・ピンチ拡大・引っ張って更新（プルリフレッシュ）を抑止する。
- 判定にはイベントの発生時刻を使う（P-17）。

**D-19 スマホ横画面の扱い【優先度B】**

| 案 | 内容 |
|---|---|
| **横画面でも遊べるが「縦画面推奨」を表示（推奨）** | コンベアは縦のまま（C-13を守る）。出土品は小さくなる |
| 横画面では一時停止して「縦にしてください」と表示 | 判別しやすさは守れるが、横で遊びたい人が遊べない |
| 横画面だけコンベアを横向きに流す | C-13（上から下）の変更になるため、ユーザー承認が必要。非推奨 |

### 6.3 見た目・音・保存

## 7. 技術構成の比較

### 7.1 候補

| 観点 | T-1：TypeScript＋Canvas 2D（自前の小さな仕組み）＋HTML/CSSのUI | T-2：TypeScript＋PixiJS（WebGL描画ライブラリ） | T-3：TypeScript＋Phaser（ゲームフレームワーク） | T-4：TypeScript＋DOM/CSSのみ |
|---|---|---|---|---|
| 容量 | 最小（ゲーム本体のみ） | 中（ライブラリが数百KB規模） | 大（数百KB〜1MB規模） | 最小 |
| 速さ | このゲームの表示数（数十個）なら十分 | 大量のスプライトや派手な演出に強い | 十分 | 要素が増えると端末により不安定 |
| 入力の即時性 | 完全に自分で制御できる | 自分で制御できる | フレームワークの入力処理を経由する（工夫すれば可） | 制御できる |
| ロジックの分離・テスト | 作りやすい | 作りやすい | フレームワークに寄りがちで、分離に工夫が必要 | 描画とロジックが混ざりやすい |
| レスポンシブUI | HTML/CSSでそのまま書ける | UIはHTML/CSSを重ねる形が楽 | フレームワーク内で作ると手間 | 得意 |
| 保守 | 依存が少なく長持ち | ライブラリの更新に追随が必要 | 同左（大きめ） | 依存が少ない |
| 学習・情報量 | 標準技術のみ | 多い | 多い | 標準技術のみ |

### 7.2 推奨：T-1

- **ゲーム画面**：Canvas 2D。出土品は起動時に画像として作り置きし、描画は貼り付けるだけにする。
- **UI**（スコア表示、ボタン、メニュー、リザルト）：HTML/CSSをCanvasの上に重ねる。レスポンシブ対応とタッチ操作がしやすい。
- **ゲームロジック**：描画やブラウザに依存しない純粋なTypeScriptのモジュール。時刻を受け取って状態を進める形にし、テストで時間を自由に進められるようにする。
- **ループ**：requestAnimationFrame。ロジックは固定刻み（例：1/120秒）で進め、描画は毎フレーム。経過時間に上限を設け、画面復帰時に一気に進まないようにする。
- **描画負荷の調整**：解像度倍率（devicePixelRatio）の上限を2にする、演出の粒子の数を画面サイズや実測フレーム時間に応じて減らす。
- **開発ツール**：Vite（開発サーバーとビルド）、Vitest（テスト）。
- **成果物**：静的ファイル（HTML/JS/CSS）一式。そのままWebサーバーやGitHub Pages等の静的ホスティングで公開できる。ローカルでは `npm run dev` または `npm run preview` で遊ぶ（ファイルをダブルクリックで開ける1ファイル版の出力も任意で追加可能）。
- **環境**：このPCに Node.js v25.9.0／npm 11.12.1 が入っていることを確認済み（2026-11-08）。開発用パッケージ（Vite、Vitest、TypeScript）のダウンロードは実装段階でユーザーに確認してから行う。

推奨理由：表示する物の数が少ないゲームなので描画ライブラリの性能は必要なく、入力の即時性とロジックのテストしやすさ、依存の少なさを優先した。
描画を分離しておくので、将来演出を大きく強化したくなった場合は、描画部分だけPixiJSに差し替えられる。

## 付録A：試算（詳細設計で確定する前の目安）

前提（仮）：判定ラインまでのコンベアの長さを論理座標で1000とする。出土品が画面上端に現れてから判定可能になるまで約2.0秒見える＋判定可能1.5秒＝計3.5秒で判定ラインに着く速さを基準速度とする。

| 項目 | 値 |
|---|---|
| 基準速度 | 1000 ÷ 3.5 ≒ 286／秒 |
| 判定エリアの長さ | 先行 0.35秒 ≒ 100、通常 1.15秒 ≒ 329、計 ≒ 429 |
| 出土品の大きさ（仮） | 160 |
| 出土品の最小間隔（大きさ＋すき間30） | 190 |
| 基準速度での出現間隔の下限 | 190 ÷ 286 ≒ 0.66秒（毎秒約1.5個） → P-07 |
| 暫定表 2.0秒間隔での間隔 | 572（画面に約2個） |
| 暫定表 2.1倍速・判定時間を秒で固定した場合の判定枠の長さ | 1.5 × 600 ＝ 900（コンベアの9割） → P-02 |
| 同・判定枠を固定した場合の判定時間 | 429 ÷ 600 ≒ 0.71秒 |
| 暫定表どおりに400個へ到達する時間 | 20×2.0＋30×1.7＋50×1.4＋100×1.1＋200×0.9 ＝ 451秒 ≒ 7.5分 → P-09 |

画面上の大きさ（目安。機種により異なる）：

| 画面 | コンベアに使える高さ | 出土品（160）の表示 |
|---|---|---|
| スマホ縦（例：幅390×高さ844） | 約520ピクセル | 約83ピクセル（約13mm） |
| スマホ横（例：高さ390） | 約330ピクセル | 約53ピクセル（約8.5mm） → P-16 |
| PC（例：1920×1080のブラウザ） | 約800ピクセル | 約128ピクセル |
